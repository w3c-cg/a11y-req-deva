Devanagari behaves differently from the Latin alphabet in ways that matter when text is read, segmented, displayed or spoken aloud. This document describes those features, for the script and for the languages written in it. It is groundwork for later requirements, and it does not present untested observations as requirements.

This is a draft developed under the Accessibility Internationalization Community Group. It is a working characteristics draft: it describes characteristics of Devanagari, and of languages written in it, and the accessibility questions they raise. It presents no settled requirements.

This version corresponds to Revision 7 of the draft, dated 11 October 2026.

Introduction

Purpose

This document is for people who write or review Web accessibility guidance for Devanagari content. Its job is to keep two things apart: script behaviour that is already established, and accessibility questions that still need testing.

It is a sibling of Accessibility Requirements for Japanese Web Content and follows the same outline, though it is stricter about evidence. None of the characteristics below is carried over from the Japanese document.

Relationship to W3C Devanagari resources

You are assumed to know the terms and concepts in Devanagari Script Resources, so the script is not described again here. This document picks out the characteristics that matter for accessibility, and the questions each one raises.

Three W3C documents cover Devanagari layout, and the Internationalization Working Group’s India Language Enablement pages (IIP) list all three:

  • Devanagari Script Resources (deva-lreq) describes the script and what its layout requires.
  • Devanagari Gap Analysis (deva-gap) records where specifications and browsers fall short. It is a Group Draft Note and describes itself as work in progress.
  • Indic Layout Requirements (ilreq), a 2020 Working Draft mainly about Devanagari, defines the orthographic syllable formally and sets out layout requirements, letter spacing among them. What it says about grapheme clusters predates Unicode 15.1.

None of the three deals with accessibility, screen readers or synthesized speech. This document addresses that gap. It builds on the three documents and does not replace them. For shaping, orthographic syllables, conjuncts and segmentation in more depth, see those documents and the Hindi orthography notes.

Script and language distinction

Devanagari is used for Hindi, Marathi, Nepali, Sanskrit, Konkani and other languages. Shaping and segmentation belong to the script, so they may hold across all of them. Pronunciation, vocabulary and grammatical register belong to each language. Language-specific observations are labelled as such, and a property documented for Hindi must not be assumed to hold for every language written in Devanagari.

Orthographic syllable

Devanagari Script Resources defines a consonant-initial orthographic syllable as the whole consonant cluster plus any following vowels and diacritics. A syllable can also begin with an independent vowel letter. Indic Layout Requirements covers both cases in a formal definition, with one more rule for a consonant followed by virama at the end of a word: V[m] | {CH}C[v][m] | CH.

This document uses the deva-lreq definition. Section 2.6 compares it with extended grapheme cluster boundaries on the tested Devanagari examples, and says what is still open beyond them.

The unit matters whenever software moves through text, or selects, deletes, highlights, spaces or breaks it. If software treats each code point as a separate visible character, it can split a sequence that the orthography treats as one syllable. Which unit is right may still depend on the operation (§2.6).

Inherent vowel, matras, and visual reordering

A Devanagari consonant carries an inherent vowel unless that vowel is changed or suppressed. Dependent vowel signs, or matras, can sit above, below, before or after the consonant. Take कि: the vowel sign is stored after the consonant, drawn to its left, and pronounced after it.

So the stored order, the visible order and the spoken order can all differ. An operation that follows the writing system keeps the consonant and its vowel sign together. How assistive technologies handle that relationship has not been tested.

Styling only part of a syllable causes a related problem. Devanagari Gap Analysis records that markup wrapped around only some characters of a syllable can separate a pre-base vowel sign from its consonant (gap #89). In Chrome 153 the shape did not break, but the partial styling was not applied as written: a style on the first part spread to the whole cluster, and a style on a vowel sign alone was lost. Other engines have not been tested, and no reader effect is claimed.

Vowel signs also reach above the shirorekha and below the baseline. The gap analysis notes that underlines and overlines need to take them into account (gap #90).

Conjuncts and virama

The virama (U+094D) suppresses the inherent vowel and can join consonants into a conjunct. Depending on the sequence and the font, you see a half-form, a stacked form, a fused ligature, or a visible virama. ZWJ and ZWNJ can change which of these appears.

So the stored sequence and what you see on screen can differ. An operation that changes visual presentation may need to keep a conjunct intact, yet a visible virama may call for a different boundary from one that forms a conjunct. Font fallback can change the visible result without changing the text.

The gap analysis states the consequence directly: “Since the underlying code points are identical if a cluster is displayed as a conjunct or instead with visible viramas, it’s not possible to distinguish one situation from another by working with the code points” (gap #115). It also records browser engines differing in which part of such a cluster they style as a first letter (gaps #94 and #115). Those are the gap analysis’s records, not results for current versions of every engine. What these differences mean for readers has not been established.

Shirorekha

Many Devanagari letters connect through the shirorekha, the line along the top of a word. Shaping draws it; it is not encoded as a character. Letters do not all meet it in the same way.

Letter spacing breaks the line between units. Indic Layout Requirements treats this as the normal look of letter-spaced Devanagari, as on signs and in decorative text: space goes between orthographic syllables and the top bar is broken (§6). A broken line under letter spacing is expected typography, not a rendering fault. Other styling can cut the joins between letters too; the gap analysis records this for text stroke (gap #139).

Whether conjuncts survive letter spacing is a separate question. The gap analysis records half-form conjuncts being split in Gecko, Blink and WebKit (gap #117), and records the underlying grapheme-cluster issue as fixed (gap #87). In Chrome 153, ten words containing conjuncts — six usually drawn as half-forms, and four usually drawn as fused or stacked forms — were letter-spaced at 0.12em and 0.5em in three fonts, and none of the conjuncts split. Safari and Firefox have not been tested. Behaviour should be recorded for each engine and version, not assumed.

The accessibility question is different again. On a sign, a designer chooses spacing for a few words. A reader using accessibility overrides may apply it to whole passages to make them easier to read. Whether a broken shirorekha then affects recognition, and for whom, needs evidence from readers. The typographic convention and the rendering tests do not answer it.

Word boundaries and line breaking: Hindi example

Modern Hindi normally puts spaces between words, so requirements written for unspaced Japanese text do not carry over. Spaces do not settle every boundary, though. Matras and conjuncts sit inside words, and compounds, punctuation, numerals and mixed-script runs all matter for selection, search, line breaking and navigation.

Ordinary practice for Hindi is described in the Hindi orthography notes (Line & paragraph layout) and in Indic Layout Requirements §4. The notes say that Hindi text is normally wrapped at word boundaries. They also say that breaking a word at the end of a line, with a hyphen, is possible but uncommon, partly because Hindi contains mostly short words. Hyphenation is much more common when Sanskrit is written in Devanagari, they add, because those words tend to be longer.

Where a word is broken, Indic Layout Requirements allows the break at an orthographic syllable boundary, with a hyphen at the break. A word that already contains a hyphen, such as नर-नारी, can break after it.

The notes say that justification is done principally by adjusting the space between words. They do not say whether high-end systems also adjust the space between characters. In the Noto Serif comparison the notes illustrate, ascenders and vowel signs, especially with tone marks, extend slightly beyond Latin ascenders and descenders, which matters for line spacing. No Devanagari-specific source on paragraph separation has been found yet.

Punctuation has its own cases. The danda (।) and double danda (॥) are expected to behave like a full stop, so no line should begin with one. Browsers have differed on whether double-clicking a word also selects the danda (deva-gap #88; ilreq §3.1).

Word-level and character-level operations should not assume that boundaries designed for English are enough. The right Devanagari boundary depends on the operation and, in some cases, on the language.

User-perceived characters

Unicode 15.1 added grapheme-break rule GB9c, which uses the Indic_Conjunct_Break property. Where a sequence matches the rule, there is no extended grapheme cluster break before the following consonant. Devanagari Gap Analysis records this change as fixing extended grapheme clusters for Devanagari, and notes that the browser engines current at the time of that Note support the new rules (gap #87). So extended grapheme clusters matter for Devanagari segmentation, but they do not answer every accessibility question.

The comparison below was made under Unicode 17 (UAX #29 Revision 47). Unicode 18.0 was published on 16 September 2026, and UAX #29 Revision 49 revises GB9c. These examples have not been segmented under that revision.

Indic Layout Requirements §2.3 gives 260 Devanagari examples. As published, 259 of them coincide with Unicode 17 extended grapheme clusters. The remaining one, the Hindi example र्त्स्न्या:, uses U+003A COLON where U+0903 DEVANAGARI SIGN VISARGA is intended; with U+0903, the sequence is one cluster. The examples come from eleven languages: Hindi, Nepali, Kashmiri, Maithili, Dogri, Sanskrit, Marathi, Santhali, Konkani, Bodo and Sindhi. They are not every possible sequence in those languages. They include reph, clusters of three or more consonants, nukta, and a consonant plus virama at the end of a word.

For the examples ilreq gives as one syllable (its Rules 1 and 2), the comparison checked that Unicode 17 produced exactly one extended grapheme cluster. For words ending in a consonant plus virama (Rule 3), it checked that the final cluster was a consonant, an optional nukta, and a virama. There are nine Devanagari examples of that rule: छन्, हुन्, गर्दैनन्, गर्छस्, राह्, ओह्, तेजस्, मरुत् and माम्. In each of them the earlier clusters also match the word’s syllables; गर्दैनन्, for example, segments as ग · र्दै · न · न्.

Apart from the published colon, then, the two units have the same boundaries on these examples. That still does not tell us which unit an operation should use. A general “use clusters” rule would go beyond this comparison, and so would a general “clusters are inadequate” rule. What remains open is narrower: sequences the examples do not cover, visible units that depend on the font rather than the encoded text, and which unit each operation should use.

Navigation, selection, deletion, speech and visual overrides each need testing against three kinds of unit: extended grapheme clusters, orthographic syllables, and the caret or glyph boundaries a renderer produces. That includes text where viramas are visible and where joiners control the form. None of these units is yet preferred for every operation. A visible virama or font fallback can change how glyphs are grouped, but not the Unicode cluster boundaries of the same encoded text. Whether readers treat the new grouping as one unit has not been tested. A requirement should name the operation and the unit suited to it.

This finding is specific to Devanagari. Indic scripts differ in their conjunct properties: Kannada, Gurmukhi and Tamil have no Indic_Conjunct_Break = Linker assignment in Unicode 15.1 through 17, and under the same Unicode 17 rules their conjunct examples in Indic Layout Requirements split into several extended grapheme clusters. The gap analysis likewise notes that the problem remains for several other scripts (gap #87). The Devanagari result must not be generalized to all Indic writing systems.

Character recognition and reading load

Matras, types of conjunct and font-dependent forms are candidate variables for recognition studies. Bhide (2018) reports an experiment in which English-speaking adults learned a semi-artificial orthography modeled on Devanagari; Nag (2022) offers a broader framework for akshara writing systems. Neither establishes an accessibility effect for children learning Devanagari, fluent adults, readers with dyslexia, readers with low vision, or assistive-technology users. Findings from Kannada are not evidence about Devanagari.

Editor’s note: No direct Devanagari reader evidence is currently cited. Practical experience, such as that of accessible-format producers and reading-support practitioners, and documented reader accounts can contribute alongside research, each with its limits stated. The evidence needed to make a presentation option available may differ from the evidence needed to prescribe one presentation for every reader. Until a population, a task, and an outcome are documented, this section is not a basis for a requirement.

Language-level characteristics

Correct BCP 47 language metadata, which the author controls, is a prerequisite for language-aware processing. It does not guarantee the right voice or pronunciation. What a listener hears also depends on the user agent, screen reader, installed voices, fallback behaviour, and how changes of language within a passage are handled.

In Hindi, schwa deletion means that an inherent vowel shown in the spelling is not always pronounced. The phenomenon, and how one text-to-speech system treats it, are documented. How current screen readers and voices handle it has not been tested in this work. The same assumption cannot be carried over unchanged to Sanskrit or other Devanagari languages.

These are language questions, not properties of Devanagari shaping. A future requirement should name the authoring condition, processing component, language and evidence, rather than treat a Hindi result as script-wide.

Letters for sounds outside the basic set: Hindi example

Devanagari’s basic consonants do not cover every sound used in Hindi. Hindi adds letters with the nukta (U+093C), a dot written below a consonant. The Hindi orthography notes say the nukta “is used to represent foreign sounds”: ज़ (z) is formed from ज and फ़ (f) from फ, and क़, ख़ and ग़ are formed the same way. Hindi also writes ड़ and ढ़ with a nukta, for the flapped sounds in सड़क and पढ़ना.

The same letter can be stored in two ways. Unicode has precomposed characters for these letters, in the range U+0958 to U+095F, but they are excluded from composition: normalization to NFC or NFD turns each into the base consonant followed by U+093C. The Hindi orthography notes report that the Unicode Standard recommends the base-plus-nukta sequence for Hindi, and they expect both forms to keep appearing in real text. In either form the nukta stays in one extended grapheme cluster with its consonant: ज़रूर segments as ज़ · रू · र.

Two accessibility questions follow, and neither has been tested in this work. Do search, find-in-page and other matching treat the two encodings as the same letter? And do current voices give a nukta letter its own sound, reading ज़ with a z rather than the sound of ज? As in the other sections, this records the characteristic; proposals for handling it belong to later requirements.
